# REL1-B offline release bundle contract

REL1-A proved the supported installer contract. REL1-B adds dependency locking,
offline assembly and release integrity without changing that runtime contract.

This document defines the bundle shape before the wheelhouse/npm-cache assembly
steps are implemented so later work has one stable target.

## Supported release identity

- Product version: `0.2.0`
- Release train: `REL1`
- Backend runtime: Python 3.11
- Frontend build runtime: Node.js 22
- Production installs exclude Python `[dev]` extras.

## Bundle layout

The final REL1-B bundle will use this shape:

```text
openjm-rel1-<version>/
  app/                         source/application payload
  python/
    requirements.lock         frozen production dependency set
    wheelhouse/                all production wheels/sdists required offline
  npm/
    cache/                     release-local npm cache populated from package-lock
  RELEASE-MANIFEST.json        sorted file list, byte sizes and SHA-256 digests
  RELEASE-MANIFEST.sha256      SHA-256 of RELEASE-MANIFEST.json
```

The exact dependency artifacts are REL1-B2/B3 work. Do not hand-author or infer
a lock file: it must be generated by a real Python 3.11 resolver and then proved
installable.

## Integrity contract

`scripts/release-integrity.py` is stdlib-only.

Generate the manifest only after the release payload is fully assembled:

```bash
python3.11 scripts/release-integrity.py generate /path/to/openjm-rel1-0.2.0
```

Verify before installation:

```bash
python3.11 scripts/release-integrity.py verify /path/to/openjm-rel1-0.2.0
```

For a trusted distribution channel, publish the manifest SHA-256 separately and
pin it during verification:

```bash
python3.11 scripts/release-integrity.py verify /path/to/openjm-rel1-0.2.0 \
  --expected-manifest-sha256 <trusted-sha256>
```

Verification fails closed when:
- the manifest or its checksum file is missing or malformed;
- a listed payload file is missing or modified;
- an unexpected payload file appears after manifest generation;
- a payload or manifest path is unsafe;
- a symlink exists anywhere in the bundle;
- the trusted manifest digest does not match.

The checksum file inside the bundle detects accidental corruption but is not an
independent trust anchor. A production release should distribute the expected
manifest digest out-of-band (for example, a signed release record).

## Remaining REL1-B acceptance

NOT RUN / not yet implemented in B1:
- Python production/development dependency resolution and frozen lock;
- wheelhouse creation and hash-checked offline pip install;
- npm offline-cache assembly and registry-blocked `npm ci`;
- final bundle assembly;
- clean Linux development installation;
- fully provisioned production Linux installation;
- Windows/WSL2 runtime installation;
- registry-blocked/offline installation;
- final browser/persona journey.

These gates must not be claimed from the integrity tests alone.
